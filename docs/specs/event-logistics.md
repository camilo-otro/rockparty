# Event logistics — equipment, roles, and the day-of checklist

**Status:** captured, not started · **Milestone:** Phase 3 — Showtime
**Builds on:** #30 (venue equipment), #49 (equipment description autocomplete),
#63 (notifications + realtime), #37 (live mode)

## The problem

An organizer books a venue and fills a setlist, and then discovers on load-in
that nobody brought a bass amp. The app currently knows what a venue *has*
(`venue_equipment`, from #30) and who is *playing* (`performance_user`), but
nothing about the gap between them: what this particular toque needs, and where
each piece of it is coming from.

Three questions per item, and today the app answers none of them:

1. **What does this toque need?** A PA, mics, a drum kit, a bass amp — and also
   a sound engineer and an MC, which are people, not gear.
2. **Where is it coming from?** The venue already provides it? The organizer is
   hauling it? One of the musicians is bringing theirs? Rented? Nobody yet?
3. **Did it actually turn up?** The day-of tick.

The valuable output is not the inventory. It is the **gap list** — the items
with no source — surfaced early enough to fix, and a checklist on the day so
nothing confirmed months ago is quietly forgotten.

## Principles this has to respect

- **Augment the humans** (CLAUDE.md). The app must not decide the logistics. It
  can *suggest* (the venue says it has a PA; the setlist implies a bass amp) but
  every requirement is the organizer's to accept, edit or delete. No
  auto-assignment of gear to people.
- **English code, Spanish UI.** `party_requirement`, `party_role`, `source`;
  labels like "LOGÍSTICA", "¿Quién lo trae?", "Checklist del día".
- **Free-tier-first.** No file uploads, no external services. This is rows and a
  couple of views.

## Model

One table for both equipment and roles. They differ in *what* they name but share
the entire lifecycle — needed → sourced → confirmed → present on the day — and
the same UI, the same gap counter, the same checklist row. Splitting them would
duplicate all of that to save one nullable column.

```sql
create type requirement_kind   as enum ('equipment', 'role');
create type requirement_source as enum ('unassigned', 'venue', 'organizer', 'performer', 'external');

create table public.party_requirement (
  id             bigint generated by default as identity primary key,
  party_id       bigint not null references public.party (id) on delete cascade,
  kind           requirement_kind not null,
  -- exactly one of these, per the checks below
  equipment_id   bigint references public.equipment (id),
  role_id        bigint references public.party_role (id),
  quantity       integer,                 -- equipment only; null = unspecified
  source         requirement_source not null default 'unassigned',
  -- who is bringing / doing it, when they are an app user
  assigned_user  uuid references public.profile (id) on delete set null,
  -- ...or a free-text stand-in when they are not: a rental company, a friend
  -- who has no account. Keeps the row useful without forcing an invite.
  assigned_label text,
  notes          text,
  confirmed_at   timestamptz,             -- the source said yes
  checked_at     timestamptz,             -- ticked off on the day
  created_at     timestamptz not null default now(),

  constraint requirement_names_one_thing check (
    (kind = 'equipment') = (equipment_id is not null) and
    (kind = 'role')      = (role_id is not null)
  ),
  -- "two mics" makes sense; "two MCs" is two rows with two names
  constraint quantity_is_equipment_only check (kind = 'equipment' or quantity is null)
);

create index on public.party_requirement (party_id);
create index on public.party_requirement (assigned_user) where assigned_user is not null;
```

**Deliberately NOT unique on `(party_id, equipment_id)`.** Two guitar amps from
two different sources are two rows; `quantity` covers multiples from *one*
source. (And a unique index over the nullable `equipment_id`/`role_id` pair would
not dedupe anyway — Postgres treats NULLs as distinct. That trap has bitten this
repo before; see the applause migrations.)

`assigned_user` references `profile`, which is the pattern `party_admin` and
`party.created_by` already use — both FK to `public.profile`, not `auth.users`.

### The role catalogue

A new lookup, seeded and world-readable, exactly like `equipment` and
`instrument`:

```sql
create table public.party_role (
  id         bigint generated by default as identity primary key,
  name       text not null,
  created_at timestamptz not null default now()
);
-- seed: Ingeniero de sonido, Presentador (MC)
```

Kept as a table rather than an enum so adding "Fotógrafo" or "Encargado de la
puerta" later is an insert, not a migration with the
`ALTER TYPE ... ADD VALUE` transaction restriction.

**Why roles are not `instrument` rows.** An instrument is something you play in a
*performance* — `performance_user` is keyed per song. A sound engineer is engaged
for the whole toque and plays nothing. Reusing `instrument` would put a
non-playing role into every song's signup list.

## RLS

The security boundary, as always in this app.

- **SELECT** — anyone who can see the party. Reuse the existing
  `can_see_party()` helper so test-data visibility (#67) is inherited for free.
- **INSERT / UPDATE / DELETE** — party admins only, mirroring the `party` UPDATE
  policy: `created_by = auth.uid()` or a row in `party_admin`.
- **The one exception: a source confirming their own item.** A musician assigned
  the bass amp should be able to say "yes, I'll bring it" without being made a
  party admin. Do this with a `SECURITY DEFINER` RPC, not a broadened UPDATE
  policy — an UPDATE policy scoped to `assigned_user = auth.uid()` would let them
  rewrite `quantity`, `notes`, or reassign the row, and RLS cannot restrict
  *which columns* an update touches.

  ```sql
  create function public.confirm_requirement(p_id bigint, p_confirmed boolean)
  returns void language plpgsql security definer set search_path = public as $$ ... $$;
  -- Touches only confirmed_at, and only where assigned_user = auth.uid().
  revoke all on function public.confirm_requirement(bigint, boolean) from public;
  grant execute on function public.confirm_requirement(bigint, boolean) to authenticated;
  ```

  **Note the `revoke ... from public`.** `create function` grants EXECUTE to
  PUBLIC and anon/authenticated inherit it, so revoking from `anon, authenticated`
  is a no-op. This exact mistake shipped once already — see
  `20260907_purge_revoke_from_public.sql`.

## Stages

### Stage 1 — the organizer's list

Schema + `party_role` catalogue + a LOGÍSTICA section on the party detail page,
admin-only.

- Add a requirement: pick equipment (from the 11-item catalogue, grouped by its
  existing `category`: sonido / backline / escenario) or a role.
- Set `source` and `notes`. No assignment to people yet.
- **Seed from the venue.** An explicit "Traer el equipo del local" action that
  creates one `source='venue'`, `confirmed_at=now()` row per `venue_equipment`
  entry, carrying its `quantity` and `notes` over.

  Explicit rather than a trigger on venue change, so it can never silently
  clobber an organizer's edits — and so re-running it after a venue swap is a
  decision, not a surprise. It needs to skip equipment already listed.
- **The gap counter**: a chip on the party page for admins — `3 sin resolver` —
  counting `source = 'unassigned'`. This is the whole point of Stage 1; the list
  without the nag is just data entry.

### Stage 2 — assigning it to people

- `assigned_user` (pick from the party's musicians and admins) or
  `assigned_label` for someone outside the app.
- **Notify the assignee** on assignment, via the existing `notification` table
  and realtime bell (#63). An assignment nobody is told about is worse than no
  assignment — it reads as done and isn't.
- `confirm_requirement` RPC + a confirm/decline control wherever a musician sees
  their own assigned items. A decline should clear `assigned_user` and drop the
  row back to `unassigned`, so it re-enters the gap count rather than sitting
  quietly declined.
- Show assigned-to-you items somewhere the musician will actually look — the
  natural spot is their toque row in "Mis toques", or the party page itself.

### Stage 3 — the day-of checklist

- `checked_at`: a tick per row, grouped by source ("del local", "lo traes tú",
  "lo trae alguien más", "sin resolver"), so on the day the organizer reads it as
  a load-in list rather than an inventory.
- Reachable from the live-mode console (#37), which is already the "run the show"
  surface, and from the party page before the show starts.
- Unresolved items stay visible and un-tickable-away, per *augment the humans* —
  the app should not let the gap disappear just because the organizer scrolled
  past it.

## Deliberately out of scope for now

- **Deriving requirements from the setlist.** A setlist with a bass signup
  implies a bass amp; drums imply a kit. Genuinely useful as a *suggestion* in a
  later stage, but it is inference about the physical world and will be wrong
  often enough that it must never create rows on its own.
- **Venue-side confirmation.** A venue admin confirming "yes, the PA will be
  there for your toque on the 19th" is valuable and would make `source='venue'`
  mean something firmer than "the venue's profile says so". It needs a
  venue-side surface, so it is its own piece of work.
- **Cost splitting.** Who paid for the rental is a different feature and drags in
  money.

## Open questions for the product call

1. **Should roles be volunteer-able rather than only assigned?** A guest putting
   themselves forward as MC mirrors how instrument signups already work, and fits
   the app's self-organising grain. It is also a materially different UI. Assign
   only, for Stage 2?
2. **Does an unresolved gap block anything?** Today a toque can be `confirmed`
   with no PA and no sound engineer. Should the gap count be purely advisory, or
   should confirming a toque warn?
3. **Should the checklist survive as a record** after the toque, for the Memories
   work (#42)? If so, `checked_at` history is already enough; if not, nothing to
   do.
